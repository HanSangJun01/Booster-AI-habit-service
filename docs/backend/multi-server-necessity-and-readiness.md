# 멀티서버 필요성 입증 & 확장 준비(scale-out readiness) 리포트

> 작성일: 2026-07-21 · 브랜치: `integration/a-b-axis`
> 목적: "멀티서버가 지금 필요한가"를 측정으로 판정하고, 근거를 하나씩 분류해
> **지금 코드로 준비할 것 / 나중에 배포에서 해결될 것**을 나눈 뒤, 실제 "미리 준비" 절차를 정리한다.
> 선행 문서: [`multi-server-considerations.md`](./multi-server-considerations.md) (위험 목록·우선순위),
> [`../monitoring/saturation-cache/saturation-redis-verdict.md`](../monitoring/saturation-cache/saturation-redis-verdict.md) (병목 분류).

## 0. 한 줄 결론

> **현 규모에서 "처리량" 관점의 멀티서버는 불필요하다** — 튜닝된 싱글서버(HikariCP pool=30)가
> 가상 SLO(8,000 RPS)를 0에러로 초과(9,131 RPS)한다. 멀티서버 필요성은 **미래 조건부**(실제 트래픽이
> 튜닝 싱글 천장을 넘을 때, 그리고 가용성 요구가 생길 때)다.
> 따라서 지금 할 일은 배포가 아니라 **"확장 준비(scale-out ready)"** — 멀티서버에서 깨지는
> **정합성 항목은 코드로 미리 닫고**, 대수 증설·LB·HA·DB 스케일 같은 **인프라 항목은 배포 시점으로 미룬다.**

## 1. 측정 근거 (무엇을 확인했나)

### 1.1 환경 & 가상 SLO
- 대상: `GET /api/challenges/{HOT}/leaderboards?type=PERSONAL` (인기 챌린지 1개의 개인 리더보드 조회, GROUP BY ~1,200 체크인 행). **읽기 경로 1개만**의 순수 포화 테스트.
- 백엔드: Docker 컨테이너, `HikariCP maximum-pool-size=30`, `open-in-view=false` (BS-30 처방 이미 반영됨).
- 호스트: 10 CPU / 8GB. **부하생성기(k6)와 백엔드가 같은 호스트를 공유** ← 측정 한계(아래).
- 가상 SLO: **8,000 RPS · p99 < 300ms · 에러율 < 1% · 지속**.

### 1.2 결과
| 측정 | 방식 | 달성 RPS | p99 | 에러 | 판정 |
|---|---|---|---|---|---|
| 기준선 | 폐루프 800 VU (think0) | **9,131** | 152ms | **0.00%** | ✅ SLO 초과 |
| 천장 탐색 | 개루프 arrival 6k→16k | **7,638** + 2,714/s 드롭 | 676ms | 0.00%(서버) | 과부하 시 처리량 정체·지연 폭증, 서버는 우아하게 저하 |

### 1.3 해석
1. **풀 튜닝이 병목을 이미 해소했다.** 옛 기록(pool=10)의 ~3,400 RPS 천장이 pool=30에서 ~2.7배로 상승 → **가장 싼 수직 레버(설정 한 줄)로 현재 병목(커넥션 풀) 제거**. 병목은 사라진 게 아니라 앱/호스트 CPU로 **이동**했다.
2. **싱글 실사용 천장 ≈ 9,000 RPS.** 더 밀어도 처리량이 안 오르고 지연만 악화 → 현재 병목은 CPU.
3. **이 천장은 호스트 CPU 공유로 저평가됐다.** 폐루프 800VU(9,131)가 개루프 4,000VU(7,638)보다 높은 유일한 이유는 k6가 백엔드와 같은 10코어를 경합했기 때문. 즉 **노트북 1대에서는 수평 확장의 처리량 이득을 공정하게 재현할 수 없다** (컨테이너 N개가 같은 CPU를 나눠 씀).

> **함의**: "처리량으로 멀티서버 필요성 입증"은 이 하드웨어에서 막다른 길이다. 억지로 하면 CPU 경합으로 오염된 숫자만 나온다. 처리량 입증은 **분리된 부하생성기 + 싱글 천장을 넘는 실목표**가 있는 **클라우드**로 이관한다.

## 2. 멀티서버 근거별 분류 — "지금 코드" vs "나중 배포"

멀티서버로 가는 정당한 근거를 하나씩 보고, 해결 위치를 나눈다.

| # | 근거 | 성격 | 지금 코드로? | 배포에서? | 이 프로젝트 판정 |
|---|---|---|:---:|:---:|---|
| 1 | **처리량/용량** | 병목 해소로 더 많은 요청 | 준비만 | ✅ (클라우드 증설) | ⏳ **미래 조건부** — 싱글이 SLO 충족. 실트래픽이 튜닝 싱글 천장 초과 시 |
| 2 | **가용성(HA)** | 1대 죽어도 서비스 유지(SPOF 제거) | 준비만 | ✅ (≥2 인스턴스+LB) | ✅ **자명한 근거** — 프로덕션이면 트래픽 무관 필요 |
| 3 | **무중단 배포** | 롤링 교체로 다운타임 0 | 준비만 | ✅ (오케스트레이터) | ✅ 2와 세트 |
| 4 | **워크로드 격리** | 웹 vs 배치/스케줄러 분리 | 🔶 일부 | ✅ | 🔶 정산 스케줄러 분리 후보 |
| 5 | **지역/지연 분산** | 사용자 가까운 리전 | ❌ | ✅ | ❌ MVP엔 과함 |
| 6 | **장애 격리** | 한 요청/테넌트가 전체 안 죽임 | 🔶 아키텍처 | ✅ | ❌ 대규모 시 |

**핵심 통찰**
- **근거는 "자명한 것"과 "측정해야 아는 것"으로 갈린다.** 가용성(2)은 논리로 자명 → 실험 불필요. 처리량(1)은 측정 필요 → 재보니 싱글로 충분.
- **대부분의 근거는 "배포에서 해결"된다** (증설·LB·리전은 인프라). **코드가 할 일은 "그 배포가 가능하도록 준비"**뿐이다 = 3장.

## 3. Scale-out 준비 항목 — 지금 "코드로" 닫을 것 (핵심)

멀티서버로 가면 **요청은 LB가 1대로 분산하지만, 상태·스케줄러·락은 인스턴스마다 독립**이라 깨진다. 이건 배포가 못 고치고 **코드로 미리 닫아야** 한다. [`multi-server-considerations.md`](./multi-server-considerations.md)의 위험 목록과 매핑:

| 항목 | 멀티서버에서 깨지는 이유 | 해결 위치 | 처방 | 우선순위 |
|---|---|:---:|---|:---:|
| **스케줄러 중복 실행** | `@Scheduled`가 인스턴스마다 독립 타이머 → N대면 정산 N번 → **코인 이중 지급** | **코드** | ShedLock `@SchedulerLock` (또는 Quartz 클러스터) | **P1** |
| **팀 구성 비결정 셔플** | `Collections.shuffle()`가 인스턴스마다 다른 순서 | **코드** | 셔플 제거 → `participant_id` 정렬 결정적 배정 | P2 |
| **참여율 Lost Update** | Team row 락 없음 → 마지막 저장이 이김 | **코드** | `@Version` 낙관적 락 + 재시도 | P3 |
| **정산 멱등 게이트 경쟁** | 두 인스턴스가 동시에 PENDING 저장 시도 | **코드** | Challenge row `PESSIMISTIC_WRITE` 락 | P4 |
| **참가자 수 카운트 경쟁** | 카운트 쿼리가 락 밖 | **코드** | 카운트를 락 이후로 이동 | P5 |
| **로컬 캐시 불일치** (Caffeine) | 인스턴스별 캐시 → evict 전파 안 됨 → 새로고침마다 값 다름 | **코드+배포** | 캐시 추상화 유지(코드) + 필요 시 Redis 공유 캐시(배포) | 조건부 |
| **DB 커넥션 예산** | `pool × 인스턴스 ≤ max_connections(100)` → pool30이면 **3대까지** | **코드(설정)+배포** | per-instance pool 산정(코드) + PgBouncer/RDS(배포) | 준비 |

> **DB 커넥션 천장은 이번에 실증됐다**: pool=30 × 3대 = 90 ≤ 100. 4대(120)면 커넥션 고갈.
> → 수평 확장은 병목을 앱 풀에서 **DB 커넥션으로 이동**시킨다. 대규모면 **PgBouncer(풀러)나 DB 스케일**이 세트.

**현재 준비 상태 요약**
- ✅ 무상태 인증(JWT) — 이미 완료 (sticky session 불필요)
- ✅ `open-in-view=false`, pool 명시 — 완료
- ❌ P1~P5 정합성 항목 — **미적용** (단일 서버라 DB 유니크 제약이 최후 방어선 역할 중)
- ❌ 캐시/커넥션 외부화 — 미적용(조건부)

## 4. "미리 준비"할 때 고려사항 (체크리스트)

배포 없이도 지금 설계에 반영해두면 나중이 싸진다. **무상태 설계는 지금 공짜, 나중 소급은 비쌈**이 대원칙.

**A. 상태(state) 외부화 — 인스턴스는 "일회용"이어야**
- [ ] 세션/토큰: 서버 메모리 세션 금지 → JWT(무상태) ✅ 이미
- [ ] 캐시: 로컬 인메모리(Caffeine)는 인스턴스별로 갈림 → 공유 필요 시 Redis. 최소한 **캐시 접근을 추상화**해 교체 쉽게
- [ ] 업로드/파일: 로컬 디스크 금지 → 오브젝트 스토리지(S3 등)
- [ ] 인메모리 카운터/집계: 금지 → DB/Redis

**B. 동시성·멱등성 — "여러 대가 동시에 같은 일"을 가정**
- [ ] 스케줄러/배치: 분산 락(ShedLock)으로 1대만 실행
- [ ] 쓰기 경합: 낙관적(@Version)/비관적 락으로 Lost Update 방지
- [ ] 비결정 로직(shuffle/random/시간): 결정적으로 (어느 인스턴스가 실행해도 동일 결과)
- [ ] 외부 호출/결제: idempotency key로 중복 방지

**C. 설정·구성 — 12-factor**
- [ ] 환경변수로 주입(DB_URL, pool, 시크릿) ✅ 부분 적용 중
- [ ] per-instance pool 산정: `pool × 최대 인스턴스 ≤ DB max_connections`

**D. 운영·관측 — 여러 대를 다룰 수 있게**
- [ ] Health/Readiness/Liveness probe (기동 완료 전엔 트래픽 안 받게) — actuator/health ✅ 있음
- [ ] Graceful shutdown (진행 중 요청 마치고 종료 → 무중단 배포 전제)
- [ ] 인스턴스별 메트릭 라벨(instance_name) — `prometheus-multi.yml`에 반영 ✅
- [ ] 로그 집계(중앙화) — 여러 대 로그를 한곳에서

**E. 데이터 계층 — 다음 병목 대비**
- [ ] 커넥션 풀러(PgBouncer) 필요 시점 인지
- [ ] 읽기 복제본/캐시로 읽기 분산 (핫키 대비, 단 verdict상 아직 시기상조)

## 5. "미리 준비" 수행 프로세스 (단계)

준비는 "코드 다 갈아엎기"가 아니라 **감사 → 우선순위 → 재현 → 처방 → 검증 → 고정**의 반복이다.

1. **감사(Audit)** — 상태·스케줄러·캐시·비결정·락 지점을 목록화. (이미 `multi-server-considerations.md`가 5개 위험으로 정리해둠)
2. **우선순위** — **금전·정합성 손실 순.** P1 스케줄러 중복(코인 이중지급) → P2 셔플 → P3 Lost Update …
3. **로컬 재현(RED)** — 멀티 인스턴스(`docker-compose.multi.yml`)를 띄워 함정을 **실제로 재현**하고 실패 테스트로 고정. 예: 3대에서 정산 스케줄러가 동시 실행돼 코인이 N배 지급되는 로그 포착. *(CPU 무관 로직 문제라 로컬에서 100% 재현 가능)*
4. **처방 구현(GREEN)** — 최소 변경으로 해결. P1이면 `shedlock-spring` + `shedlock-provider-jdbc-template` 의존성 추가, 스케줄러에 `@SchedulerLock`.
5. **검증** — 3의 재현이 사라졌는지 확인 + 성능 회귀 없는지.
6. **회귀 방지** — 동시성 테스트로 고정. 이미 `backend/src/test/concurrency/`에 C1~C6·F4가 있어 확장 지점으로 좋음.
7. **문서화 + 인덱스** — 결정·처방을 기록하고, project-memory 디렉티브/AGENTS 인덱스에 연결(이미 D1 등록됨).
8. **배포 항목은 Deferred 목록으로** — LB·HA·오토스케일·PgBouncer·Redis 인프라는 "클라우드 배포 시" 태그로 분리. **지금 구현하지 않는다.**

## 6. 결론 (verdict)

| 질문 | 답 |
|---|---|
| 지금 처리량 때문에 멀티서버가 필요한가? | ❌ **아니다** — 튜닝 싱글이 SLO(8k) 초과(9.1k, 0에러) |
| 로컬에서 처리량 확장을 증명할 수 있나? | ❌ CPU 공유로 불가 → 클라우드로 이관 |
| 가용성 때문에 언젠가 필요한가? | ✅ 프로덕션이면 자명(SPOF 제거) — 배포에서 해결 |
| 그럼 지금 뭘 하나? | ✅ **scale-out 준비** — P1~P5 정합성 항목을 코드로 닫기 |
| 준비의 핵심 한 줄 | **"지금 여러 대 두기"가 아니라 "언제든 여러 대로 갈 수 있게 무상태·멱등·분산락으로 준비"** |

**다음 액션(권장)**: 5장 프로세스의 3~4단계 — 멀티 스택으로 **P1(스케줄러 중복 정산)을 재현→ShedLock으로 해결**. 로컬에서 정직하게 증명 가능한 유일한 "멀티서버 대비" 작업이며, 가장 큰 위험(금전 손실)을 먼저 제거한다.
