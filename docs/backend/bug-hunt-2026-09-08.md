## 🔴 1. 구제 만료가 코인을 여러 번 깎을 수 있다

두 결함이 한 세트로 움직인다. 하나만 고치면 절반만 막힌다.

### 1.1 `WeeklyGoalScheduler` 에 분산락이 없다

```
ChallengeEndScheduler   @SchedulerLock ✅  markEndedChallenges / retryFailedSettlements
WeeklyGoalScheduler     @SchedulerLock ❌  세 개 모두
  ├ 0 1 0 * * MON   evaluateLastWeek     주간 채점
  ├ 0 10 0 * * *    expireOverdueRescues 구제 만료 확정   ← 문제
  └ 0 5 0 1 * *     runMonthly           무료 구제권 지급
```

`docker-compose.multi.yml` 로 3대를 띄우면 세 작업이 인스턴스마다 각각 돈다.

채점(`evaluateUser`)과 월간 지급(`runMonthly`)은 멱등 가드가 있어 중복 실행을 견딘다
(회귀 테스트도 있다). **`expireOverdueRescues` 만 견디지 못한다.**

### 1.2 `expireOverdueRescues` 의 재확인이 작동하지 않는다

```java
List<WeeklyEvaluation> overdue = evaluationRepository
        .findByResultAndRescueDeadlineLessThanEqual(PENDING_RESCUE, now);   // ① 락 없이 조회

for (WeeklyEvaluation evaluation : overdue) {
    User user = userRepository.findByIdForUpdate(userId).orElse(null);      // ② User 를 잠금
    if (user == null || !evaluation.isPendingRescue()) {
        continue;   // ③ "락 대기 중 사후 구매가 먼저 확정함" — 실제로는 걸러내지 못한다
    }
    evaluation.markFailed();
    streakRepository.findById(userId).ifPresent(Streak::reset);
    coinService.charge(userId, missPenalty, WEEKLY_MISS_PENALTY, null);     // ④ 벌금 -500
}
```

③이 무력한 이유: `evaluation` 은 ①에서 락 없이 읽은 스냅샷이고, **User 에 락을 걸어도
`WeeklyEvaluation` 은 다시 읽히지 않는다.** JPA 영속성 컨텍스트에 남아 있는 옛 사본을
그대로 본다. 주석은 안전하다고 믿고 있지만 아니다.

**다중 인스턴스**

```
A: 목록 조회 → X = PENDING_RESCUE
B: 목록 조회 → X = PENDING_RESCUE      (같은 스냅샷)
A: 락 → ③ 통과 → markFailed + charge(-500) → 커밋
B: 락 → ③ 통과 (자기 사본은 여전히 PENDING) → 또 charge(-500)
                                                합계 -1000
```

**단일 인스턴스에서도 좁게 재현된다.** 스케줄러 풀이 1스레드라 자기 자신과는 안 겹치지만,
사용자의 **사후 구매**(`purchaseLateRescue`, 1,200코인)와는 겹친다. 00:10에 구매로 구제됐는데도
벌금이 또 나가고 스트릭이 0이 된다.

### 고치는 방향

`@SchedulerLock` 세 개를 붙이면 다중 서버는 막히지만 **사후 구매와의 경합은 남는다.**
둘 다 필요하다:

1. `WeeklyGoalScheduler` 세 메서드에 `@SchedulerLock`
2. 락을 잡은 뒤 evaluation 을 다시 읽거나,
   `UPDATE weekly_evaluations SET result='FAILED' WHERE id=? AND result='PENDING_RESCUE'`
   의 영향 행 수가 1일 때만 벌금을 매기도록 바꾼다 (DB 레벨 멱등)

## 🟡 2. 검증 구멍 두 개

| 항목 | 지금 | 근거 |
|---|---|---|
| `description` | **길이 제한 없음** | DB 가 `TEXT`, DTO 에 `@Size` 없음. `title` 은 `@Size(max=200)` + `VARCHAR(200)` 인데 비대칭. 5,000자 소개글이 그대로 저장됐다 |

둘 다 당장 사고는 아니지만, 상한 없는 입력이 그대로 DB 로 들어가는 자리다.

## ✅ 깨끗한 것 — 58개 항목

실서버에 실제로 호출해서 확인했다.

**오늘 새로 넣은 코드 (20/20)**
- 참가 → 취소 → 재참가를 3회 반복해도 **잔액 == 코인 거래내역 합**
- 방 해산 시 환불 정확히 1회, 두 번 눌러도 409 (이중 환불 없음)
- 해산된(CANCELLED) 방에 재참가 차단
- 위치 예약: 마지막 예약이 이김 / 같은 값이면 취소 / 예약한 장소에서는 아직 인증 불가
- 탈퇴한 참가자가 있던 방도 정상 해산

**팀 흐름 (17/17)** — 개발보고서가 75~90%로 적은 구간
- 10명 채우니 **READY → ACTIVE 자동 전환**, **5:5 편성**
- 팀 상세(내 팀·상대 팀·멤버 5명), 팀 리더보드 2팀, 개인 리더보드 10명
- 팀 체크인도 `PENDING` + `submissionId` 반환 (위치+사진 고정이 팀에도 적용됨)
- 반경 밖 팀 체크인 400, 정원 찬 뒤 참가 409, ACTIVE 챌린지 해산 409

**권한 (4/4)** — 비참여자의 참가자 명단·팀 상세 조회, 남의 방 해산·참가 취소 전부 차단

**입력 검증** — 이메일 형식, 비밀번호 8자, 닉네임 1~30자·공백, 좌표 범위,
반경 10~1000m, 예치금 100 이상, 정원 10 고정 전부 정상

**상점·승인** — 잔액 부족 거절 / 800 차감 / 구제권 증가,
방장 승인 PENDING → 대기자 목록(닉네임 포함) → 승인 → 재승인 409

## 기록해 둘 것

사냥 중 "버그 2건"으로 보고했다가 **철회한 게 있다.** 프로브가 `approvalType` 을
`approval` 로 잘못 보내 챌린지가 AUTO 로 만들어진 것이었다. 필드명을 맞추니 방장 승인
흐름은 정상이었다.

부수적으로 확인된 사실: 서버는 **모르는 필드를 조용히 무시한다**(Spring 기본값).
다만 실제 필드가 `@NotNull` 이면 누락으로 400 이 나므로, 오타로 조용히 넘어가는 건
**선택 필드에 한정**된다.
